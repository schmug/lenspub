# LensPub Glossary

This document defines the normative vocabulary used throughout the LensPub repository. Where a term is defined here, other documents use it in exactly this sense. Terms are capitalized in specification text when used normatively.

## Normative language

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **NOT RECOMMENDED**, **MAY**, and **OPTIONAL** in LensPub specification documents are to be interpreted as described in BCP 14 ([RFC 2119](https://www.rfc-editor.org/rfc/rfc2119), [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174)) when, and only when, they appear in all capitals.

## Core terms

### LensPub
The open protocol and ecosystem for publishing, exchanging, and applying user-owned interpretation layers, defined by this repository.

### Interpretation
The act of enriching rendered content with user-controlled meaning signals — annotations, summaries, evidence indicators, counterpoints, source expansions — without altering the content itself. Interpretation is a user-agent-side, post-render overlay stage operating on the rendered document (DOM and accessibility tree). It is not a network layer.

### Lens
A user's interpretation layer considered as a whole: a Lens Manifest together with the private Adaptation State accumulated under it. Informally, "my lens."

### Lens Manifest
The primary exchange object of LensPub. A portable, declarative, model-agnostic policy document that expresses a user's interpretation intent. A Lens Manifest is never model weights and never a prompt (ADR-0001). It is history-free: it MUST NOT contain browsing history or state from which reading history can be reconstructed (ADR-0006). Serialized as JSON conforming to `schemas/lens-manifest.schema.json`; media type `application/lens-manifest+json` (provisional).

### Lens Engine
A runtime that applies a Lens Manifest to rendered content, producing Interpretation Results. Engines may be rule-based, local-model, cloud-model, or hybrid. Engines are conformance-classed by capability tier; the protocol is engine- and model-agnostic.

### Interpretation Result
The structured output of a Lens Engine for a given content target: zero or more Overlay Annotations plus a Reasoning Trace and a Reproducibility Envelope. Serialized as JSON conforming to `schemas/interpretation-result.schema.json`.

### Overlay Annotation
A single unit of interpretation anchored to a span or region of content, expressed as a profile of the W3C Web Annotation Data Model (ADR-0002). Overlay Annotations are layered above content; they MUST NOT rewrite, obscure by default, or reorder the underlying content.

### Anchor
The association between an Overlay Annotation and a location in content, expressed with W3C Selectors (TextQuoteSelector, TextPositionSelector, CssSelector, XPathSelector, RangeSelector) plus the robust-anchoring fallback strategy defined in the Lens Engine specification.

### Reasoning Trace
The human-readable explanation attached to an Interpretation Result or Overlay Annotation stating *why* the engine produced it — which manifest rule, priority, or signal triggered it. Required for explainability.

### Reproducibility Envelope
Metadata that MUST accompany every Interpretation Result, recording engine identifier and version, model identifier and (where available) hash, generation parameters, and prompt-template identifier. Makes model drift visible rather than silent (ADR-0004).

### Adaptation
The process by which a Lens evolves. Adaptation is never silent: it proceeds only through Lens Change Proposals reviewed by the user under the manifest's Adaptation Policy.

### Adaptation Policy
A named, parameterized setting governing how readily a lens may evolve. Five policies are defined — **Locked**, **Conservative**, **Balanced**, **Adaptive**, **Explorer** — as points on the protocol-defined parameters *proposal frequency*, *evidence threshold*, and *auto-accept ceiling* (ADR-0010). Policies may be set lens-wide and overridden per Domain Scope.

### Domain Scope
A named subject area (e.g., politics, technical research, entertainment) to which per-domain adaptation policies or interpretation preferences attach. Domain Scopes are declared in the manifest; content classification into scopes is an engine responsibility and MUST be explainable.

### Lens Change Proposal
A structured, reviewable proposed modification to a Lens Manifest, generated by a Lens Engine from explicit user feedback and evaluation. Carries evidence, a diff against the current manifest, and the outcome of any shadow evaluation. Accepted proposals become new manifest versions. Serialized as JSON conforming to `schemas/lens-change-proposal.schema.json`; device-local Adaptation State, never exchanged, and therefore without a media type.

### Adaptation State (Lens Deltas)
Private, device-local state accumulated as a lens learns: pending proposals, feedback records, evaluation data. Stored as explicit, reviewable deltas layered on the manifest core. Adaptation State is never part of the shareable manifest (ADR-0006).

### Lens Diff
A structured comparison between two Lens Manifests (or two versions of one), conforming to `schemas/lens-diff.schema.json`. Diffs operate on history-free manifest cores only and therefore never expose browsing history.

### Lens Version
An immutable, content-addressed snapshot of a Lens Manifest identified by semantic version and hash. Every accepted Lens Change Proposal produces a new version; rollback to any prior version MUST be supported.

### Subscription
A standing relationship in which a user's lens incorporates a published lens (expert, organization, partner, collaborative, or public) as a composable input. Subscriptions are user-initiated, inspectable, revocable, and never require sharing browsing history. Subscription transport is protocol-agnostic in v1; AT Protocol is the reference binding.

### Published Lens
A Lens Manifest made available for subscription or copying, optionally signed. Variants: **Expert Lens** (individual authority), **Organization Lens**, **Partner Lens** (mutual/collaborative), **Public Lens** (open export).

### Signed Manifest
A Lens Manifest carrying a proof under W3C Verifiable Credential Data Integrity, with issuer identity expressed as a DID (ADR-0003). Verification requirements are defined in the Security Model.

### Lens Publisher
An identity (DID) that publishes lenses. Trust in publishers is explicit, user-granted, and revocable.

### Provenance Signal
An externally verifiable indicator about content origin or evidence quality that an engine may surface — e.g., C2PA Content Credentials, citation presence, source identity. LensPub consumes provenance signals; it does not adjudicate truth (ADR-0007).

### Capability Tier
A declared conformance class of a Lens Engine (e.g., rule-based, local-model, hosted-model) describing which manifest features it can honor. Manifests declare intent; engines declare capability; the same manifest may yield different richness of interpretation at different tiers (ADR-0004, Architecture spec).

### Trust Boundary
Any point where content or lens data leaves the user's device or local process — most importantly, opt-in cloud inference (ADR-0005). Crossing a trust boundary MUST be explicit, per-domain, revocable, and visible to the user.

### Local-First
The design default that interpretation runs on the user's device with no network dependency; remote services are enhancements, never requirements (ADR-0005).

## Naming conventions

- Object type names are PascalCase in schemas (`LensManifest`, `LensDiff`, `InterpretationResult`, `LensChangeProposal`).
- The provisional namespace for identifiers and media types is `https://lenspub.org/ns/` — provisional until the project registers its permanent home.
- Specification documents refer to decisions as **ADR-NNNN**, found in `/adr`.
