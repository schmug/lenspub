# Reference Implementation: Browser Proof of Concept

**Status:** Draft v0.1 · **Date:** 2026-07-09 · **License:** CC-BY 4.0

This document describes the LensPub reference implementation: a browser extension, in [`/poc`](../poc/README.md), that demonstrates the protocol end to end at the rule-based capability tier. It records what the proof of concept implements, maps each source file to the specification text it embodies, identifies the conformance classes it does and does not satisfy, and states its limitations. The prose of this document is licensed CC-BY 4.0 like the rest of the specification; the code it describes is licensed Apache-2.0 (see [ADR-0009](../adr/0009-licensing-and-governance.md) and [`LICENSE-CODE`](../LICENSE-CODE)).

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, NOT RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in all capitals.

## 1. Purpose

The proof of concept exists to establish three claims made throughout this repository, in running code rather than prose. First, that a Lens Manifest is genuinely model-agnostic: a purely rule-based engine, with no model of any kind, can consume the same manifest a model-backed engine would and produce useful, schema-conformant interpretation ([ADR-0001](../adr/0001-manifest-is-declarative-policy.md), [ADR-0004](../adr/0004-reproducibility-envelope.md)). Second, that interpretation works as a user-agent-side, post-render overlay stage: the implementation reads the rendered DOM, never rewrites or reorders content, and can be dismissed leaving the page byte-identical ([ADR-0008](../adr/0008-interpretation-is-overlay-stage.md)). Third, that the transparency obligations are implementable at small cost: every Overlay Annotation carries a Reasoning Trace citing the manifest fields (as JSON Pointers) that triggered it, and every Interpretation Result carries a Reproducibility Envelope.

The browser was chosen as the first target for the reasons recorded in the constitution: lowest barrier to entry, and the browser naturally sits at the interpretation boundary. The extension is a Manifest V3 package of vanilla JavaScript — no build step, no dependencies, no remote code — loadable directly via `chrome://extensions`. It performs no network I/O whatsoever: the only `fetch()` calls load bundled `chrome-extension://` resources. It therefore exhibits the local-only privacy default of [ADR-0005](../adr/0005-local-only-default.md) in its strongest form, by not containing a remote code path at all.

The proof of concept is a reference, not a product. Where the specification permits a range of engine quality — anchoring robustness, extraction fidelity, summary depth — the PoC deliberately implements the simplest conforming behavior and labels it as such in its own reasoning traces.

## 2. Conformance classes implemented

The [LensPub Protocol specification](../spec/lenspub-protocol.md) defines conformance classes; the PoC implements two of them.

**Manifest Consumer.** The extension loads, structurally validates, inspects, imports, and exports Lens Manifests conforming to [`schemas/lens-manifest.schema.json`](../schemas/lens-manifest.schema.json). The popup surfaces the manifest as the user-legible object the protocol says it is: name, `lensVersion`, adaptation `defaultPolicy`, and the full JSON, read-only. Import applies PoC-level structural validation (required members `lenspub`, `type`, `metadata`, `interpretation`, `adaptation`) with human-readable rejection messages; full JSON Schema validation is exercised in the test suite rather than shipped in the extension.

**Lens Engine, rule-based capability tier.** The engine core compiles the declarative manifest into engine-internal rules and produces Interpretation Results conforming exactly to [`schemas/interpretation-result.schema.json`](../schemas/interpretation-result.schema.json): `highlight` annotations for priority-term matches, `evidence-indicator` annotations (each with a `basis`, never a verdict — [ADR-0007](../adr/0007-epistemic-stance.md)) for source-list matches and for the `requireProvenance: ["citations"]` heuristic, and a document-level extractive `summary`. Anchoring follows the robust-anchoring fallback of [ADR-0002](../adr/0002-profile-web-annotation.md): exact match, whitespace-normalized `degraded` match, or visibly `unanchored` presentation in the lens panel — never silent guess-anchoring.

The PoC does **not** implement the Lens Publisher class or any part of the sharing, signing, subscription, adaptation, or diff machinery. Specifically out of scope, with the documents that specify them: subscriptions and published lenses ([Lens Manifest specification](../spec/lens-manifest.md)); Signed Manifests and verification ([ADR-0003](../adr/0003-adopt-vc2-dids-for-trust.md), [Security Model](../security/security-model.md)); Lens Change Proposals and the entire adaptation workflow ([Adaptation Model](../spec/adaptation-model.md), [ADR-0010](../adr/0010-adaptation-policies-parameterized.md)); Lens Diff ([Lens Diff specification](../spec/lens-diff.md)); model capability tiers and remote inference with its per-Domain-Scope opt-in ([Lens Engine specification](../spec/lens-engine.md), [Privacy Model](../security/privacy-model.md)). A conforming rule-based engine MAY omit all of these; what it MUST NOT omit — reasoning traces, envelopes, anchoring honesty, overlay-only rendering — is exactly what the PoC concentrates on.

Two structural properties of this layout are themselves demonstrations. The four `engine/` modules are pure and DOM-free: the same files execute in the extension's service worker and under Node in the test suite, showing that a Lens Engine core is separable from any particular host. And the compiled rule set produced by `compile.js` (regular expressions, origin matchers, resolved flags) never leaves the engine: only the manifest is portable, exactly as [ADR-0001](../adr/0001-manifest-is-declarative-policy.md) requires of compiled artifacts.

## 4. The capability-tier seam

[`model-engine.stub.js`](../poc/engine/model-engine.stub.js) is deliberately shipped as a throwing stub rather than omitted. It documents, at the precise point in the code where a WebLLM-class or on-device model tier would attach, the contract such a tier inherits: the same compiled-rules input, the same InterpretationResult output schema, reasoning traces and `basis` requirements unchanged, and a Reproducibility Envelope that MUST change to tell the truth — `capabilityTier: "local-model"`, a `model` member with identifier and obtainable hash, generation `parameters`, and a `promptTemplate` identifier for the compiled prompt. The stub also restates the boundary a model tier cannot cross without ceremony: `execution.location` remains `local` absent an explicit, per-Domain-Scope, revocable opt-in recorded as `optInScope` ([ADR-0005](../adr/0005-local-only-default.md)). The seam thus makes concrete the central portability claim of [ADR-0004](../adr/0004-reproducibility-envelope.md): the same manifest yields richer interpretation at higher tiers, and the envelope is what keeps that difference visible instead of silent.

## 5. Test coverage

`node poc/test/run-tests.mjs` runs 26 assertions-based tests with no test framework. They cover: the Manifest Compiler (priority, source, and provenance compilation; presentation defaults; origin matching including subdomains, full origins, DIDs, and hostless URLs; structural rejection of non-manifests with readable errors); the Interpretation Pipeline against synthetic blocks (a priority match, an uncited-statistic block, a cited block, and a plain block — asserting annotation kinds, non-empty reasoning on every annotation, `basis` on every evidence-class annotation, and that every `manifestRefs` JSON Pointer resolves to a real location in the manifest); the Anchor Manager (selector production with 32-character context, exact location disambiguated by context, whitespace-mangled content resolving as `degraded` with correct offsets, and honest `unanchored` misses) — string-based, with no DOM dependency; and the envelope (required fields, tier, local execution, absent `model` and `promptTemplate`). Finally, the suite validates the bundled lens against `lens-manifest.schema.json` and three produced results (trusted-origin, distrusted-origin, and empty-page) against `interpretation-result.schema.json` using Ajv with the 2020-12 dialect. The DOM-side behaviors that Node cannot reach — overlay host creation, range wrapping, explanation cards, clean unwrap on dismissal — were additionally exercised with a browser-automation smoke pass during authoring, but the Node suite is the maintained, required bar.

## 6. Limitations

The PoC's honesty obligations extend to this document. Term matching is literal and case-insensitive; it has no notion of topical relevance beyond string proximity to the declared priority. The uncited-claim rule is a stated heuristic — sentences containing numbers or percentages inside blocks with no hyperlinks — that will both miss claims and flag benign sentences; its reasoning trace says so on every firing. Summaries are first-sentence extraction, labeled as such. Domain Scopes are declared in the bundled manifest but not used for content classification, so per-domain priorities apply globally and per-domain adaptation policies are displayed rather than enforced (nothing in the PoC adapts). Extraction is capped at 200 blocks and results at 50 annotations; interpretation runs once per page load and does not track client-side navigation or DOM mutation. Anchoring degrades systematically on pages whose source whitespace differs from rendered text — the documented fallback, visibly marked, rather than a defect. None of these limits are protocol limits; each marks the distance between the floor this reference establishes and the engine quality the [Lens Engine specification](../spec/lens-engine.md) invites.
